# themify

Switches my whole setup between the color themes defined in `bin/themes/*.conf`.

Themes: **sora**, **cendre** (originals) · **mocha** (Catppuccin), **nord**, **gruvbox**, **dracula**, **kanagawa** (curated from their official palettes).

```bash
themify          # pick a theme interactively (gum/fzf if present, numbered menu otherwise)
themify sora     # apply a theme by name
themify cendre
```

The engine is stateless: it applies exactly the theme you name, nothing more.
Callers without a terminal (e.g. Raycast) must pass the theme name explicitly —
a bare `themify` with no tty exits with a usage error.

## Adding a theme

Drop a `bin/themes/<name>.conf` (data only) with all 31 roles + ANSI_0–15, then run `themify/build.sh` to generate its ghostty theme. The engine never changes; it discovers themes by globbing `bin/themes/*.conf`.

A conf is the **complete palette** — 31 roles, no tool mentioned: core (`BG` `BG_ALT` `BG_SEL` `FG` `FG_MUTED` `BORDER` `ACCENT` `ACCENT_2`), status (`ERROR` `WARN` `OK` `INFO`), hues (`RED` `GREEN` `BLUE` `YELLOW` `ORANGE` `MAGENTA` `CYAN` `PURPLE` `SAGE` `ROSE` `GOLD` `PEACH` `TEAL` `STEEL` `SHADOW`), surfaces (`HIGHLIGHT` `BG2` `BAR_BORDER` `POPUP_BG` `POPUP_BORDER`). Consumers derive alpha layers themselves; confs store pure colors.

The engine derives every tool's format from these roles (tmux `mode-style` = `fg=$FG,bg=$BG_SEL`, pane borders = `$BORDER`, borders `active_color` = diagonal gradient `0xFF$ACCENT` → `0xFF$ACCENT_2`, hlchunk = `$ACCENT`, …) and uses the **theme's own name** for everything that isn't a color — convention: all per-theme artifacts are named after the theme (ghostty theme file, nvim/vim colorscheme, bat/btop/yazi/hunk/lazygit/fzf/delta variants, wallpaper `wallpapers/<name>.*` — absent means no wallpaper). The tmux status bar is deliberately NOT themed (fixed tokyo-night "night"); only its copy-mode selection and pane borders follow the theme.

Ghostty theme files are GENERATED — run `themify/build.sh` after adding or editing a theme (output is committed, so checkouts work without it). No other color artifacts exist. an nvim colorscheme, and `<name>.*` variants for bat/btop/yazi/hunk/lazygit/opencode/delta (generated by remapping the sora artifacts to the new palette).

## What it touches

| Tool | File | How it applies |
|------|------|----------------|
| sketchybar | `sketchybar/colors.lua` | flips `local theme`; colors.lua reads this package's conf at runtime (shared roles, single source) , then `sketchybar --reload` |
| tmux | `tmux/tmux.conf` | recolors copy-mode `mode-style` + pane borders (bar itself is fixed tokyo-night "night"), then `tmux source-file` |
| nvim | `nvim/lua/plugins/colorscheme.lua` | rewrites the LazyVim colorscheme, and live-switches every running nvim through its socket |
| vim | `~/.vimrc` | swaps the `colorscheme` line, applies on next vim launch (colorschemes live in `~/.vim/colors/`) |
| hlchunk | `nvim/lua/plugins/hlchunk.lua` | comments/uncomments the color pair (chunk + line numbers) |
| bat | `bat/config` | swaps the `--theme` value (next `bat` call uses it) |
| btop | `btop/btop.conf` | swaps the `color_theme` path, applies on next launch |
| yazi | `yazi/theme.toml` | copies the palette variant from `yazi/themes/` over it, next launch |
| hunk | `hunk/config.toml` | copies the palette variant from `hunk/` over it |
| lazygit | `lazygit/config.yml` | copies the palette variant from `lazygit/` over it, next launch |
| obsidian | `obsidian-vault/.obsidian/appearance.json` | swaps `cssTheme`, applies on Obsidian restart |
| opencode | `opencode/tui.json` | swaps the `theme` value, applies on next launch |
| git-delta | `~/.gitconfig` | swaps the included palette gitconfig, next `git diff` uses it |
| borders | `borders/bordersrc` | rewrites `active_color` (ACCENT→ACCENT_2 gradient), then pushes it to the running daemon |
| pi | `~/.pi/agent/settings.json` | swaps the `theme` value (theme files live in `~/.pi/agent/themes/`), applies on next launch |
| wallpaper | `wallpapers/current-theme.jpg` | overwrites this fixed file with the theme image, then restarts WallpaperAgent |
| ghostty | `ghostty/config` | swaps the theme, then reloads the front window |

sketchybar, tmux, nvim, borders and ghostty update live (ghostty needs the Accessibility permission described below). bat, hunk and git-delta are CLIs, so their next invocation picks up the change. hlchunk, btop, yazi, lazygit, opencode and pi apply on their next launch. Obsidian applies its theme (`Sora` or `cendre`) on restart.

yazi, hunk and lazygit switch by copying a whole theme-file snapshot (`<palette>.toml` / `<palette>.yml`) over the live config, so edits to non-color settings in those live files get overwritten on switch. Keep such edits in the per-palette snapshots instead.

## Per-theme values

- **sora**: ghostty theme `sora` (background `#0e1018`), border `#80C8E0`, tmux copy-mode `bg=#1e2430`, hlchunk `#80C8E0`, wallpaper `stellar_sora.png`.
- **cendre**: ghostty theme `cendre` (background `#171311`), border `#EA9875`, tmux copy-mode `bg=#2f1e17`, hlchunk `#EA9875`, wallpaper `tangerines.jpg`.

bat, btop, yazi, hunk, lazygit, opencode and git-delta each use their matching palette named `sora` or `cendre`. git-delta's `syntax-theme` points at the bat theme of the same name.

gh-dash is not wired: it has no color config and follows the terminal's ANSI colors, so it already tracks ghostty.

Each ghostty theme file under `ghostty/themes/` embeds its own background, so the script only swaps the `theme` line and the config has no `background` line of its own.

## Notes

- **ghostty** has no reload command, so the script presses its reload keybind (`super+shift+,`) with osascript. That needs Accessibility permission for Ghostty (System Settings > Privacy and Security > Accessibility). Without it the script prints a reminder and you press `cmd+shift+,` yourself.
- **hlchunk** picks its color at setup time and has no live recolor, so its change shows after the next nvim launch. The rest of nvim recolors right away.
- **wallpaper** works by swapping the bytes of one fixed file, `wallpapers/current-theme.jpg`, then restarting WallpaperAgent. This keeps the macOS "apply to all Spaces" mode intact, so every Space follows. One-time setup: open System Settings > Wallpaper, pick `current-theme.jpg`, and enable it for all Spaces. The script never calls System Events, which is what used to reset that mode. Setting the picture directly would only cover the focused Space.
- Every edit is guarded by an anchor check. If a file is missing, or a line was renamed and the pattern no longer matches, the script warns on stderr and skips that tool instead of failing silently.

## Adding a tool

1. Add the file path near the top of `bin/theme`.
2. Add the per-theme value as a key in every `bin/themes/*.conf`.
3. Add a generic tool block that reads that key, wrapped in `anchor '<regex>' "$FILE" '<label>'` so it fails loud, not silent.

The script is macOS only: it relies on BSD `sed -i ''` and osascript.
